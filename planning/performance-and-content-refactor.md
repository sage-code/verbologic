## 2. Target model

### 2.1 One unit, many views (the reversible / non-reversible model)

The unit of content is a **unit** (word, phrase, letter, sentence). It is stored **once**, with a per-language map. Direction is a *topic property*, not a per-language record fan-out.

```yaml
# content/dictionary/CH01T01/topic.yaml      (84 files for the dictionary instead of thousands)
code: CH01T01
level: A1
mode: reversible            # reversible | directional   (replaces langs / sourceLang)
kind: word
units:
  - id: W001
    term: { en: hello, es: hola, it: ciao, fr: salut, de: Hallo, ru: Привет, hu: Szia, pt: Olá, ro: salut }
    ipa:  { en: "/həˈloʊ/", ro: "/saˈlut/" }
    tts:  { ro: "…" }                     # ttsText respelling, only where Edge TTS needs it
```

```yaml
# content/lectures/LT01T01/topic.yaml
code: LT01T01
mode: directional            # exists *about* one language; cannot be flipped
target: ro
phonetic: true               # second column = IPA
units:
  - id: L001
    term: { ro: A }
    ipa:  { ro: "/a/" }
    gloss: { en: "first letter…", de: "…" }   # explanations, NOT equivalent terms
```

| | `reversible` | `directional` |
|---|---|---|
| Meaning | `term` is a set of equivalents; any language can be learned, any can be the gloss | `term[target]` is the subject; other languages carry explanations (`gloss`) |
| Valid learner pairs | every (target, native) with both terms present | `(target, any native)` only |
| "Swap direction" UI | allowed | hidden |
| Missing language | row shows but is disabled (structure-first policy, unchanged) | n/a |
| Replaces | default | `sourceLang`, `langs`, `phonetic`-ownership, `EN_CANONICAL` special cases |

The client derives the table rows for a `(target, ui)` pair from the unit; nothing is pre-multiplied at build time. Non-reversible content therefore needs no special code in the index, the routes or the search — it is just a topic whose `mode` is `directional`.

### 2.2 Authoring formats

| Data | Format | Why |
|---|---|---|
| Units (terms, IPA, TTS overrides, gloss) | **YAML, one file per topic** | Compact flow-maps (`{ en: hello, es: hola }`), comments allowed, one diff per topic, easy bulk edit. Replaces thousands of `item.json`. |
| Prose articles | **Markdown, as now**: `content/<track>/<TOPIC>/<ID>/<locale>.md` | Unchanged authoring. Front matter shrinks to `title, summary, status, sourceSha, order, related, video, image`. `track/topic/article/locale/entity_id/terms` are all derivable from path + `topic.yaml` and are dropped (kills F6 and the "front matter must match path" validation). |
| Letter/alphabet explanations | **Data, rendered by a component** (no `.md`) | The alphabet JSON is already the authoring surface; render `LetterArticle.vue` from unit + note. Removes the generator and 3,267 files (F5). |
| Generated media facts (`bytes`, `sha1`, `status`, published key) | **`media.lock.json` per topic, committed, machine-written only** | Separates authored from generated (F7). Review diffs show only real changes. |
| Topic/chapter structure and names | `structure.yaml` per track (chapter → topic codes, level, layout); topic `names` live beside the topic | One place per fact; `lastIndex` leaves the authored file. |

### 2.3 Media folder

- **Paths do not change**: `media/<track>/<CH>/<TOPIC>/<ID>/sound/<lang>.mp3` stays, so every R2 key and existing public URL is unchanged — no re-upload.
- The URL is **derived**, not stored: `root + track/CH/TOPIC/ID/sound/<lang>.mp3` (matches the emitted `…/dictionary/CH01/CH01T01/W001/sound/en.mp3`). Payloads store only *which languages have a published file*.
- `item.json` is retired in favour of `topic.yaml` (authored) + `media.lock.json` (generated). `run media manifest/upload/verify/prune` read the lock.
- `scripts/generate-audio.py` reads `ttsText`/`ipa` from `topic.yaml` instead of per-item manifests.

### 2.4 Runtime payloads

```
public/data/v/<hash>/
  index.json                 counts only: track → topic → [langs available]        (~20 KB raw)
  <track>/<TOPIC>.json       one row per unit:  { i, t:{lang:term}, p:{lang:ipa}, a:[langs with audio], d?, tg? }
  <track>/search.json        same row shape, trimmed (id, topic, t, p, a)           (~250 KB raw / ~59 KB gz for dictionary)
  <track>/titles.json
```

- Minified, no `generated` timestamp (deterministic → true no-op rebuilds), content-hashed directory, `public/_headers` with `Cache-Control: public, max-age=31536000, immutable` for `/data/v/*`.
- `ids` and `progress` leave `index.json`; entity id = `<TOPIC>:<id>` is computed. Bulk check-all reads the topic payload it already needs.
- `mime`, `bytes`, `sha1`, `section`, `source` are dropped. `mime` for video/image is implied by `kind`/track.

### 2.6 One loader, many emitters

Replace the four tree-walkers with one `scripts/lib/content-graph.mjs` that loads `structure.yaml`, `topic.yaml`, `*.md` front matter and `media.lock.json` once into an in-memory graph (with an mtime/hash cache). `media-index`, `validate-data`, `missing-content`, `lecture`, and `nuxt.config.ts` route enumeration all consume the graph. Path rules exist in exactly one place.

# Revision 2

## 7. Static vs dynamic rendering on Cloudflare

**Facts checked** ([limits](https://developers.cloudflare.com/workers/platform/limits/index.md), [changelog](https://developers.cloudflare.com/changelog/2025-09-02-increased-static-asset-limits/)): Workers Static Assets allows **20,000 files per version on Free, 100,000 on Paid** (Wrangler ≥ 4.34 for the higher limit), 25 MiB per file. `wrangler.toml` today is assets-only (no `main`), the cheapest and fastest mode. I do not know which plan you are on — that decides how much headroom there is.

**Where the file limit actually bites.** After Phase 3 the non-article output is small. The problem is only the article tail: 858 × 9 target × 9 explanation locales = 69,498 pages, which exceeds even the Paid limit, and would also dominate build time.

| Option | SEO | Speed | Cost / complexity | Verdict |
|---|---|---|---|---|
| **A. Everything static** (today) | Best | Best (no compute) | Breaks at ~20k–100k files; build time grows linearly | Right for hubs, topic lists, hot articles |
| **B. Full SSR on Workers** | Fine (HTML is server-rendered) | Cache hit ≈ static; miss = Worker CPU | Needs `main` script, runtime content access, Workers request quota | Overkill for the whole site |
| **C. Hybrid (recommended)** | Fine, if every URL stays crawlable (sitemap + hreflang) | Static for tier 1, cached SSR for the tail | Medium: one spike, one config change | **Recommended** |

**Hybrid design.**
- **Tier 1 — prerendered (static):** track/chapter/topic pages and article pages for the explanation locales that matter most (e.g. `en` plus the learner's top locales), for every target language. Roughly 858 × 9 × (2–3) ≈ 15–23k at full size; tune against your plan's limit.
- **Tier 2 — on demand (Worker + edge cache):** the remaining (target, explanation-locale) pairs render on first request, are cached (`Cache API` / Nuxt `routeRules` SWR), and are listed in sharded sitemaps with `hreflang` alternates so they stay indexable.
- **Never dynamic:** anything that changes only on deploy and is needed by crawlers on day 1.
- Static asset requests are free and unlimited on Workers; Worker invocations count against the request quota (verify current Free/Paid numbers) — the cache hit ratio is what keeps this cheap.

**Unknowns the spike must answer (1–2 days, before committing):**
1. Can Nuxt Content (SQLite at build) serve article bodies inside a Worker (D1 binding?) — or should articles be precompiled into one JSON AST per article (`/data/v/<hash>/articles/<TOPIC>/<ID>.json`, all locales) that the Worker or the client renders? I lean to the precompiled JSON: it removes the Content database from the runtime path entirely and also makes tier-1 builds faster.
2. Measured TTFB cache-miss vs cache-hit from a Worker, and prerender time per 1,000 routes today.
3. Whether the Windows `EPERM` prerender-cache collision (noted in `nuxt.config.ts`) gets worse or better with a smaller prerender set.

**Gate:** stay fully static if the full-size route count, at a realistic locale tier, stays under ~15k files and the build stays acceptable; otherwise adopt C. Re-evaluate when per-user rendering (personalised practice) is needed — that is the other legitimate reason for a Worker.

## 8. Generation pipeline (translation, templates, sound)

### 8.1 What exists today (audit of `scripts/generate-audio.py`, `scripts/lecture.mjs`)

| Area | Today | Weakness |
|---|---|---|
| Translation | Gemini `generateContent`, default `models/gemini-3.5-flash-lite`, batches of 8, `temperature 0.2`, JSON mime type, shape/keys validated, 3 retries | Translates **bare strings with no sense/definition** (homonyms: *bank*, *light*, Romanian *ac*); no glossary/style guide; no semantic check; fence-stripping regex instead of a response schema; source language = first non-empty in `LOCALES` order; only names/descriptions — **article bodies are not machine-translated** (`lecture.mjs translate` only reports sync state) |
| Audio | Edge TTS neural voices, one voice per language, gender picked by topic-number parity | **Sequential**; existing file ⇒ skipped, so editing a term leaves **stale audio** unless `--overwrite`; no verification that the audio says the term; no loudness/silence normalisation; generates all 9 languages even when only some are needed; no `<phoneme>` support (known) |
| Articles | Hand-written MD; letter articles from a fixed template | No generation template for words/phrases/grammar/stories; no provenance |
| Review state | `status: draft|reviewed`, `sourceSha` staleness | No `machine`/`checked` rungs, no record of which model/prompt produced a text |

### 8.2 Translation accuracy — levers, in order of impact

1. **Translate a sense, not a string.** Every unit gets `sense` (English gloss + part of speech + one example sentence) in `topic.yaml`. All locales are produced from `sense` + canonical English term, never from another translation (no chains).
2. **One style guide + glossary per language**, versioned in `generation/locales/<lang>.yaml`: register (`te`/`ön`, `tu`/`vous`, *dumneavoastră* vs *tu*), **pt-PT not pt-BR** (the TTS voice is pt-PT), German noun capitalisation, Hungarian definite conjugation, Russian ё/stress marks policy, **Romanian ș/ț with comma-below (U+0219/U+021B), not cedilla (ş/ţ)**, Hungarian ő/ű (not õ/û), French spacing before `? ! : ;`, Spanish `¿ ¡`. Glossary pins fixed terms (e.g. the platform's own vocabulary: *lecture, topic, chapter*).
3. **Structured output**: use Gemini's `responseSchema` (enum of locale codes, required fields) instead of regex-stripping fences; retries only on transport errors, a separate repair pass on validation errors.
4. **Deterministic checks before any human sees text** (cheap, catch most defects): NFC normalisation; forbidden-codepoint lists per language (the cedilla case above); script check (Cyrillic for `ru`); `{{term}}`, `:target-term{…}` and other MDC/placeholder tokens preserved verbatim; length ratio vs English within a band; no English leakage in non-English fields; IPA matches `/…/` with allowed symbols; term in `topic.yaml` equals term in article front matter.
5. **LLM critic pass with a different model/prompt** (§8.5): for each locale, "does this translation preserve the sense? list defects", returning pass/fail + reason. Fails go to a review queue, not to publish.
6. **Status ladder**: `machine` → `checked` (passed 4+5) → `reviewed` (a human). Stored with `model`, `promptVersion`, `generatedAt`. Staleness still uses `sourceSha`. The site can later show a "machine-translated" marker for `machine`/`checked`.
7. **Human sampling, not human reading of everything.** You are the Romanian native: review **100% of Romanian and 100% of English canonical**; spot-check **~10%** of every other locale per chapter (random sample, plus every item the critic flagged). Record the error rate per language per chapter — it decides whether a language needs a heavier review next chapter.

### 8.3 Sound accuracy and performance

Accuracy:
- **Round-trip ASR verification.** After synthesis, transcribe the clip (a Gemini audio-input call, or Whisper) and compare the transcript to the intended `ttsText ?? term` after normalisation. Mismatches are flagged for a `ttsText` respelling (the only lever with Edge TTS) or a voice swap. This replaces ear-checking every file. Treat ASR as a *filter*, not truth: a word can pass ASR and still sound odd — hence a 5% listen sample per language per chapter.
- **Cache key = hash(text actually spoken, voice, engine, engine version, normalisation version)**, recorded in `media.lock.json`. Change a term → only that clip regenerates; nothing is silently stale.
- **Post-process every clip**: trim leading/trailing silence, loudness-normalise to one target (e.g. ffmpeg `loudnorm`), fixed sample rate/bitrate. Without this, clips from different engines/voices play at different volumes — a real UX problem in a repeat-loop player. (ffmpeg availability on your machine is unverified.)
- **Per-language voice policy file** instead of gender-by-topic-parity: one primary voice per language so the same word always sounds the same across topics.
- **Gemini TTS is a candidate, not an assumption.** Official models now: `gemini-3.8-flash-tts`, `gemini-3.8-flash-lite-tts` (stable), 2.5 TTS (still served). It supports prompt-based style control, but I did not verify word-level pronunciation control, so run a **bake-off**: ~30 hard words per language (diacritics, stress, loanwords) through Edge vs Gemini TTS, blind-listen, pick per language. Gemini TTS output is raw audio that must be converted to mp3 (verify format on the pilot).

Performance:
- Replace the sequential loop with a **bounded-concurrency worker pool** (start 4–8 in flight; Edge TTS tolerates parallel sockets but throttles aggressively — back off on `NoAudioReceived`).
- **Generate audio only for languages that need it now.** Every unit has 9 terms but a listener only hears the clip in the language being learned. Generate Romanian and English first; mark others `audio: pending` and fill when that language's track is promoted — about 7/9 less synthesis up front.
- **Batch API for text jobs** (50% price, async), one request per batch of ~25–50 units rather than 8, because shared context (style guide, glossary) is then amortised.
- Keep all outputs atomic-written and resumable (`--resume`), so a rate limit mid-chapter costs minutes, not a restart.

### 8.4 Templates for generators

Move from "free prose" to **typed templates** in `generation/templates/<kind>.yaml`. A template defines the sections, constraints and prompt fragments; the model fills a JSON schema; a renderer turns the filled sections into the MD the site already consumes. Because the translation step translates *fields*, not Markdown, formatting and structure are identical in all locales and `:target-term` / `{{term}}` tokens cannot be mangled.

| Template | Sections (each with word/length limits) | Notes |
|---|---|---|
| `word` | register & use · 2 example sentences (with L1 gloss) · common mistake · collocations · cultural note (optional) | Example sentences must use only vocabulary of the same or earlier level (see below) |
| `phrase` / `sentence` | when to use · formality · variants · reply | Pairs with Q&A topics |
| `letter` / `sound` | **no generation** — data-driven component (Phase 3) | IPA/spelling facts come from data, not an LLM |
| `grammar` (lectures) | rule in 1–2 sentences · pattern table · 3 graded examples · exceptions · quick check | Table is data, not prose |
| `story` | title · level · controlled-vocabulary prose · comprehension questions | Hardest; do last |

Shared template controls: **CEFR level** (word/clause length, tense allowed), **controlled vocabulary** (the generator receives the set of terms from earlier chapters at the same/lower level plus the current unit list and may not introduce new target-language words in examples), **learner-L1 notes** only where interference is common (e.g. Romanian *a fi* vs Spanish *ser/estar*), banned-content list, and the locale style guide from §8.2. Each template is versioned (`promptVersion`); changing it marks affected units for regeneration via the cache key, not by hand.

## 9. Content generation order

**Your preference — chapter by chapter, with translation and sound in the same pass — is right.** It gives a deployable, testable slice each time and lets the error data from one chapter tune the next. Two refinements:

1. **Stages inside a chapter are ordered; languages inside a stage are not.** Run each stage for all languages at once (they share glossary and batch context, cost is trivial, and per-language sequencing only delays learning from errors). But **gate the stages**, because an error in the canonical text is multiplied ×9 downstream:

| Stage | Output | Gate before the next stage |
|---|---|---|
| 1. Units | `topic.yaml`: term(en), `sense`, level, kind | You review English (fast — it is short and the source of truth) |
| 2. Translation | `term`/`ipa`/`tts` for all 8 other locales | Deterministic checks pass; critic flags triaged; Romanian 100%, others 10% sample |
| 3. Articles | English canonical via template, then translated fields ×8 | Same checks; you read the English and Romanian |
| 4. Audio | Only for languages being promoted (start `ro`, `en`) | ASR round-trip ≥ agreed threshold; 5% listen sample; mismatches get `ttsText` |
| 5. Publish | `./run.sh media manifest/upload`, build, verify rendering (curl the page) | Chapter checklist below |

2. **Pilot on `CH01` (dictionary).** It already holds ~80 units, so it can calibrate prompts, glossaries, voices and thresholds on content you know. Don't scale before the pilot's error rate is known.

**Track order:** Dictionary → Lectures → Stories. Dictionary supplies the controlled vocabulary the later tracks draw on, and curriculum levels line up chapter-for-chapter (see `manual/curriculum.md`). Stories are last: long-form, hardest to verify automatically.

**Per-chapter definition of done:** all stages passed; 0 deterministic-check failures; critic-flag backlog empty or explicitly waived; sampled error rate recorded; audio manifest `published` for the promoted languages; page rendered and spot-checked in the browser; chapter tagged in git.

**What not to do:** one language at a time across the whole dictionary (delays defect discovery, repeats review overhead 9×); all types at once for the whole site (nothing deployable until the end).

### 11.3 Batching — already how it works; tune, don't redesign

`gemini_translate_batch` already sends 8 items per request and asks for **all missing locales for each item in one JSON response** — one word → 8 languages in one call. Keep that (the model sees all languages together and keeps register consistent), with these changes:
- **25–40 units per request** (not 8): the shared style guide/glossary is amortised, ~3 requests cover CH01. Do not go much larger — long outputs degrade accuracy and a failure costs more.
- **Per-locale validation, per-locale repair:** if only `hu` fails a check, re-ask for `hu` of those units, not the whole batch.
- Each unit carries `sense` (§8.2), so homonyms resolve.
- Use the Batch API (50% off) for bulk chapters; synchronous for the pilot so you can watch results.
- Traffic is not a problem at this scale (a few requests per chapter); the limiting factors are accuracy and review time.
